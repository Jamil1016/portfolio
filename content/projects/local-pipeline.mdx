## The Problem

Nightly ingestion of millions of rows from the Swift Projects API (plus Gmail, Google Calendar, and Google Forms) into a Postgres warehouse, feeding analytics views consumed by internal dashboards and an AI assistant. The naive approach — a single Python script pulling everything sequentially — took roughly six hours, regularly timed out, and silently dropped data when the upstream API returned more than ~1,000 rows for a single date range.

Today it's a fleet of ~12 scheduled pipelines: orgs/projects, asset-tasks, timer, QA forms, user priorities, calendar-leave, timer-discrepancies, open-items snapshots, and Gmail-driven AR-aging + sales. Each one must be parallel, idempotent, and observable — failure of one extractor can't take down the others, and re-running has to produce the same result every time.

The whole fleet was migrated off Windows Task Scheduler (2026-05-28) onto GitHub Actions, fired by Google Apps Script time-driven triggers — the on-prem box was a single point of failure no one could see fail. A single `asyncpg` pool (min=4 / max=20) runs on a dedicated background event-loop thread so synchronous extractor code can submit queries via `run_coroutine_threadsafe()`. A `ThreadPoolExecutor` runs extractors in parallel, streaming rows over asyncpg's binary `COPY` protocol into six schemas: `data_raw` (JSONB) → `data_staging` (normalized) → `analytics` (views + materialized views), plus `reference`, `pipeline`, and `agent`. After extraction, a backfill pass resolves derived foreign keys, then materialized views refresh one at a time.

## The pipelines

Each pipeline has its own source and extraction method; they share the warehouse, the `asyncpg`/COPY machinery, and the GitHub Actions + Apps Script trigger layer — which is why this is one platform, not twelve scripts.

| Pipeline | Source | What it does |
|---|---|---|
| orgs / projects | Swift API | Org + project master data |
| asset-tasks | Swift API | The core dataset (~2.2M rows/night); per-day chunked to dodge the truncation cap |
| timer | Swift API + Google Form | Labor timer entries; real-time corrections/dedup via a Form `onFormSubmit` hook |
| QA forms | Google Forms | Quality-form submissions |
| user priorities | Swift API | Task-prioritization signals |
| calendar-leave | Google Calendar | Leave events, AI-normalized into structured rows |
| timer-discrepancies | derived | Reconciles timer entries against expected values |
| open-items snapshots | Swift API | Point-in-time open-item state for the reports |
| AR-aging + sales | Gmail | Finance figures parsed out of inbound emails |

## Key Decisions

- **Per-day API chunking.** The Swift API silently truncates a wide date range at ~1,000 rows — no error, just fewer rows. The timer extractor splits each range into one API call per calendar day, which sidesteps the cap entirely. Cost: more API calls. Benefit: zero silent data loss.
- **asyncpg on a background thread, not in-process.** A large synchronous extractor codebase couldn't be rewritten fully async at once. Running one pool on its own event loop and bridging via `run_coroutine_threadsafe()` lets sync callers stay sync while the DB layer is fully async and thread-safe.
- **Atomic clear+reload via a data-modifying CTE.** The full-refresh tables used to clear in a separate auto-committed `DELETE`, then `INSERT`. When the big `INSERT` later hit `statement_timeout`, the table was already empty — committed. Folding the clear into the insert as `WITH cleared AS (DELETE ... RETURNING 1) INSERT ...` makes clear-and-reload one statement: a timeout rolls back both, so a table is never left empty.
- **Six-schema split.** `data_raw` holds unmodified API responses; `data_staging` holds transformed rows; `analytics` holds views and MVs; `reference`, `pipeline`, and `agent` hold lookups, run metadata, and assistant metadata. Every layer is rebuildable from the one beneath it.
- **Write-once derived IDs.** Once a foreign-key resolution lands on a row it never changes, so it survives clear+reload patterns and prevents cascading rewrites downstream.

## Code Samples

Async DB pool on a background event-loop thread, with retry on transient startup failures, letting synchronous callers reach asyncpg:

```python
class PipelineDB:
    def start(self):
        self._thread = threading.Thread(target=self._run_loop, daemon=True, name="db-loop")
        self._thread.start()
        if not self._ready.wait(timeout=30):
            raise RuntimeError("Database pool failed to initialize within 30s")

    async def _create_pool(self):
        for attempt in range(1, 4):                 # 3 attempts, 5s/10s backoff
            try:
                self._pool = await asyncpg.create_pool(
                    DSN, min_size=4, max_size=20, command_timeout=300,
                    init=_init_connection, ssl=ssl_ctx,
                )
                return
            except Exception:
                if attempt == 3:
                    raise
                await asyncio.sleep(5 * (2 ** (attempt - 1)))

    def _run(self, coro):                            # sync bridge
        return asyncio.run_coroutine_threadsafe(coro, self._loop).result()
```

Atomic clear+reload — a `statement_timeout` can no longer empty the table:

```python
# A separate DELETE then INSERT can leave the table EMPTY if the INSERT
# times out after the DELETE commits. The CTE makes it one statement.
sql = (
    f"WITH cleared AS (DELETE FROM {SCHEMA_STAGING}.stg_asset_tasks RETURNING 1) "
    f"INSERT INTO {SCHEMA_STAGING}.stg_asset_tasks (...) "
    f"SELECT ... FROM {SCHEMA_RAW}.raw_asset_tasks WHERE run_id = $1"
)
db.execute(sql, run_id, statement_timeout=900)
```

Connection-level retry with exponential backoff and automatic pool reconnect:

```python
def retry_db(fn, max_retries=5, description="operation"):
    for attempt in range(max_retries):
        try:
            return fn()
        except (asyncpg.ConnectionDoesNotExistError, asyncpg.InterfaceError, OSError):
            if attempt == max_retries - 1:
                raise
            time.sleep(min(2 ** attempt, 15))
            reconnect_db()
```

## Metrics

- **Asset-task volume:** ~2.2M rows ingested per night (raw JSONB ~2.4 GB).
- **Server-side transform:** 2.2M rows transformed in ~2–3 minutes, down from ~44 minutes when the same logic ran in Python.
- **Analytics surface:** ~17 staging tables and 9 materialized views feeding dashboards and the assistant.
- **Schema evolution:** ~100 numbered SQL migrations (001 → 098) across six schemas.

## What I Learned

- **Silent truncation bugs hide in the small.** The API never returned an error — it just returned fewer rows than asked. Comparing per-day counts against expectation was the only way to catch it. Validate row counts as a first-class signal, not an afterthought.
- **Atomicity is a correctness property, not a nicety.** A two-statement clear-then-reload looks fine until the reload times out and you're staring at an empty table in production. Folding the delete into the insert with a data-modifying CTE made the failure mode impossible.
- **Sync-async bridging is a real pattern, not a hack.** Pure-async rewrites of large sync codebases stall. A pool on a background event loop unlocks async DB access inside sync callers with one helper class.
